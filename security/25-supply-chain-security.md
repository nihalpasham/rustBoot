# Supply Chain Security & Provisioning

## Summary

Secure provisioning of device identity and keys at manufacturing. Chain of
trust from silicon fabrication to field deployment. Reproducible builds with
signed software artifacts. SBOM (Software Bill of Materials) generation and
verification.

## Motivation

The strongest cryptographic protections are worthless if the device is
provisioned with a compromised key or ships with unverified firmware. Supply
chain attacks are among the most damaging because they compromise devices
before they reach the end user.

## Design

### Provisioning Flow

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│ HSM / Key   │     │ Provisioning │     │ Device       │
│ Server      │────▶│ Station      │────▶│ (blank MCU)  │
│ (secure     │     │ (secure      │     │              │
│  facility)  │     │  factory)    │     │              │
└─────────────┘     └──────────────┘     └──────────────┘
                           │
                    ┌──────┴──────────┐
                    │ Actions per device: │
                    │ 1. Program bootloader   │
                    │ 2. Burn OTP Device Identity Key │
                    │ 3. Program golden partition │
                    │ 4. Set RDP Level 2 (lock) │
                    │ 5. Verify provisioned state │
                    │ 6. Sign device certificate │
                    └──────────────────────────┘
```

### Provisioning Steps

| Step | Operation | Verification |
|------|-----------|--------------|
| 1 | Flash rustBoot bootloader | SHA-384 of flash = known good |
| 2 | Burn OTP DIK (32 bytes, generated by HSM) | Readback verify (if RDP not yet locked) |
| 3 | Flash golden recovery image | Signature verify on device |
| 4 | Set option bytes (RDP Level 2, IWDG lock) | Readback verify |
| 5 | Generate device certificate (HSM-signed) | Certificate signature verify |
| 6 | Lock provisioning interface | Hardware lock |
| 7 | Final test: cycle power, verify boot | Boot OK + attestation works |

### HSM Integration

All cryptographic signing is performed by an HSM (Hardware Security Module):

| Operation | HSM Role |
|-----------|----------|
| Device Identity Key generation | Generate random 32B, store securely, copy to OTP |
| Device certificate signing | Sign device public key with HSM-protected factory CA key |
| Firmware signing | Sign firmware images with HSM-protected code signing key |
| Provisioning verification | Verify provisioned device is genuine |
| Key backup/disaster recovery | Secure escrow of device identity keys (optional) |

### Reproducible Builds

```bash
# Build process:
cargo build --release --target=thumbv7em-none-eabihf
sha256sum target/thumbv7em-none-eabihf/release/rustboot > rustboot.sha256

# Verification (by provisioning station or end user):
docker run --rm -v $(pwd):/build rustboot-builder \
    /bin/bash -c "cargo build --release --target=thumbv7em-none-eabihf && sha256sum /build/target/release/rustboot"
# Compare against published checksum
```

### SBOM (Software Bill of Materials)

Generated with `cargo cyclonedx`:

```bash
cargo cyclonedx --output sbom.xml --spec-version 1.5
```

SBOM is signed and published with each release. Contains:
- All direct and transitive dependencies
- License information
- Vulnerability references (via cargo-deny)
- Build environment metadata

### Code Signing

| Artifact | Signing Key | Algorithm |
|----------|-------------|-----------|
| rustBoot binary | Firmware signing HSM key | LMS + ECDSA |
| Firmware image | Firmware author's key | LMS + ECDSA |
| Device certificate | Factory CA key (HSM) | ECDSA P-384 |
| Release tag (git) | Developer PGP key | Ed25519 |
| SBOM | Developer PGP key | Ed25519 |

## Verification

### Testing Requirements

- Provision flow: device is correctly provisioned (all steps verified)
- Reprovision: attempt to reset OTP (RDP Level 2 prevents this)
- Build reproducibility: same commit → same binary hash
- SBOM: all crate dependencies are listed with correct versions

### CI Integration

- Each CI run: `cargo build --release` + hash comparison against known-good
- `cargo deny check` for banned licenses and dependencies
- `cargo audit` for vulnerability advisories
- `sbom.sh` for CycloneDX generation
- `verify.sh` for build reproducibility check

## Status

- **Reproducible builds**: Implemented (sbom.sh, verify.sh)
- **SBOM generation**: Implemented (cargo cyclonedx)
- **Code signing**: Partially implemented (ECDSA signing via rbsigner)
- **HSM integration**: Not started
- **Factory provisioning process**: Not documented
- **Device certificate infrastructure**: Not implemented

## Residual Risk

- Factory provisioning is a physical security problem. A compromised
  provisioning station can inject backdoored keys. Mitigation: HSM-based
  key generation, air-gapped provisioning network, video surveillance.
- The supply chain for the MCU itself (STMicroelectronics) is trusted.
  A backdoor in the STM32 silicon would compromise all devices regardless of
  software protections. This is an accepted residual risk.
